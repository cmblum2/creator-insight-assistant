# Creator Insight Assistant — RAG over creator & comment data

**Live demo: https://creator-insight-assistant.onrender.com** *(free tier — first request
after idle takes ~30s to wake)*

🌐 Part of my portfolio → **[cmblum2.github.io/camryn-portfolio](https://cmblum2.github.io/camryn-portfolio/)**

A creator-sampling **decision desk**: who should get product next, why, whether it makes money, which
paid campaigns to scale or cut, what buyers are saying — and a one-click weekly report that turns all
of it into a document a non-technical team can act on. Under the hood: deterministic ordinal-ranked
recommendations with encoded guardrails, grounded cited RAG answers, a full unit-economics layer
(ROI, LTV, a controlled-test readout, drift monitoring), GMV-Max campaign verdicts, voice-of-customer
NLP, a reverse creator-lookup, an LLM copilot, and a printable agency report — all on a dashboard built
for a 10-minute daily workflow. Synthetic twin of a production decision engine I built for a retail
brand's affiliate program (ordinal creator ranking, epsilon-greedy sampling with exploration,
matched-control diff-in-differences lift measurement) — all data here is generated by
`scripts/gen_data.py`.

> **What to look at first:** the [live demo](https://creator-insight-assistant.onrender.com) opens on
> the **Decision queue** (act-today list), and the **⬇ Agency report (PDF)** button in the top bar
> prints the whole thing. The RAG + evaluation story is below.

**v2 guardrails (encoded, and eval-enforced):**
- **Ordinal-only ranks** — scores order creators; they never size spend.
- **Matched controls are protected** — recommending a control creator would contaminate the
  seeding-lift measurement, so the engine refuses to, and `eval/test_guardrails.py` proves it
  under every product filter.
- **No double-seeding** — already-seeded creators are excluded and flagged.

**v3 — from revenue to profit (the commercial layer):** a dashboard (`static/index.html`) with a
KPI strip, workflow-grouped tabs, and a health bar, backed by four endpoints:
- **`/economics`** — turns each sample's incremental (refund-adjusted) GMV into **ROI, payback, LTV,
  a retention curve, size-the-prize, and a margin×cost sensitivity grid**. Named drivers: net margin =
  40.5% product contribution − 10.5% affiliate commission = 30%; sample cost is a flagged, stress-tested
  assumption. The honest headline: the median sample *loses money* and only ~30% are ROI-positive, so
  blended ROI sits near breakeven (**~0.74×** on this synthetic cohort) — a power-law where a few
  winners carry the whole program, which is exactly why the ranking matters: the model's job is lifting
  that hit rate.
- **`/holdout`** — *how you prove it drives value.* A retrospective natural experiment (engine top-tier
  vs bottom-tier rank → realized profit, Welch test + CI) **plus** a pre-registered randomized-holdout
  design with power sizing (`app/experiment.py`), so the leap from "strong causal correlation" to
  "proven incremental value" is one controlled test away.
- **`/drift`** — *how you know it still works next month.* PSI on model features + causal-skill decay +
  hit-rate drop vs a saved baseline.
- The controlled readout is the headline proof: engine top-tier picks beat bottom-tier by **+$61 per
  sample** (95% CI [$33, $89], significant), and the recommender's rank-IC (Spearman rank ↔ realized
  lift) ≈ **0.38**. Everything is 100% synthetic but uses the exact math and framing of the production
  engine.

## v4 — the full decision desk (campaigns, voice-of-customer, reporting, and an LLM copilot)

v3 answered "which sample, and does it pay?" v4 turns the app into the whole desk an affiliate manager
runs each morning — paid campaigns, sampling, customer signal, and a report to hand up the chain.

**Act — one ranked to-do list.** `/decisions` merges every signal into one queue: **GMV-Max campaign
verdicts** (SCALE / TUNE / CUT / RETARGET / GATE, derived from ROAS vs target vs breakeven, with a
guard that sends breakeven > 8 to GATE instead of a nonsensical "raise the target"), **spark timing**
(the 8–14-day post-age sweet spot), and **sampling picks** — each row in plain English with the *exact*
change to make (`→ raise the goal to ≥ 2.74×; it loses money below breakeven`). `/allocate` splits a
budget across paid vs sampling by marginal profit (and leaves money unspent when no next dollar is
profitable); `/spark` and `/post_funnel` and `/heterogeneity` back the timing / ship→post→sale funnel /
subgroup-CATE views.

**Voice of the customer.** `/voc` mines the comment corpus into a category mix, a **competitor board**
(which rival brands buyers name), and price/praise themes; `/theme_lift` regresses comment-theme mix
against real video conversion (Spearman + Bonferroni) — the validated finding is that
**competitor-comparison comments predict *lower* conversion (r ≈ −0.46)**, i.e. comparison-shopping is a
warning sign, not a buy signal; `/voc_actions` splits that into *validated* (changes ranking) vs
*qualitative* (briefs humans), and `/intent` reports buy-intent density. The classifier itself is a
**v2 lexicon** (`app/intent.py`): intent-to-buy now requires a first-person subject (kills "you need to
get one…"), confirmed-purchase is split from buying-now (kills "…I just bought one" mislabels), and
praise is split from interest — pinned by `tests/test_intent_lexicon.py`.

**Reverse lookup.** `/creator?handle=` is the mirror of the recommendation flow — the engine's dossier
on *one* creator, in three honest tiers: (1) if it's in the ranked shortlist, the identical
rank/outlook/evidence a pick shows; (2) if it's in the roster but not scored, real metrics + a
*playbook outlook* explicitly labeled "estimate, not a model score"; (3) history-only or an honest
not-found. Handle-validated, cached per normalized handle.

**LLM copilot** (grounded, and degrades to a clear no-key note): `/brief` writes a creator brief
(hook / proof / preempt / CTA) grounded in a product's top videos + buy-intent comments and preempts
the top competitor; `/explain` grounds any queue verdict in that target's real audience comments (the
"why?" button); `/query` answers one question across comments + video content + campaign verdicts with
per-source citations.

**One-click weekly Agency Report** — `/report` (HTML) and `/report.pdf` (printed via a headless
Chromium baked into the image) render a **quant-desk report**, not a status page: a sparkline
scoreboard with month-over-month deltas colored by whether the direction is *good*; "three moves this
week" (biggest STOP / best BOOST / the seeding play sized in expected dollars); **problems ranked by
dollars at stake**; the full action queue with the exact `→` change highlighted; weekly VoC theme cards
+ per-campaign quotes; a **maturation-aware trend desk** (outcomes lag ~40 days, so the last two months
are trimmed for lagged metrics only and marked †, so a false $0 can't poison the trend); a forward-30-
days plan; and a model-diagnostics appendix. Because the ranker is deterministic-ordinal there are *no*
learned weights to show, so the appendix honestly shows rank-IC / precision@K / calibration-by-rank /
holdout CI / drift instead. `/ops_brief` returns a ready-to-post Discord "morning brief" embed (the
scheduler stays a dumb fetch-and-post), and `/samples_in_flight` powers a shepherding radar of shipped
samples (sold / posted / cold / waiting) with a nudge list.

**A dashboard built for the workflow, not the data model.** Five UX passes on `static/index.html`:
plain labels with the technical term as a subtitle + a shared glossary (same 13 terms as the report);
one chip component and a sticky command bar; a **"Your daily 10 minutes"** checklist with live counts
and an "I want to…" task nav; tab attention-dots that light only when a tab needs a human; and a
phone-responsive layout. Everything is guarded per-panel — one dead feed costs one panel, never the
page.

| New endpoint | What it returns |

## Stack
| Layer | Tool |
|-------|------|
| Embeddings + vector store | **Chroma** (local sentence-transformers — no embedding API key) |
| Retrieval → answer graph | **LangGraph** (MMR diversity-aware retrieval) |
| LLM (grounded generation) | **Claude** (Anthropic API) |
| API + UI | **FastAPI** + a tiny static chat page |
| Evaluation | **RAGAS** (faithfulness / answer-relevancy / context-precision / context-recall) |
| Weekly report | headless **Chromium** (`--print-to-pdf`, baked into the image) — one-click HTML + PDF, no Python PDF deps |
| Deploy | **Docker** → Render/Fly/Railway |

## Data
Synthetic, public-safe creator + comment data generated by `scripts/gen_data.py` (3,000
comments seeded with buy-intent + hair-care mentions so queries return real results). No real
creator data is used or committed.

## Run it
```bash
python -m venv .venv
. .venv/Scripts/activate            # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env                # then paste your own key into .env (gitignored)

python scripts/gen_data.py          # -> the full synthetic contract (creators, comments, campaigns,
                                    #    videos, outcomes, roster, sample_requests, monthly_trends, ...)
python -m app.ingest                # -> builds the Chroma index (no API key needed)
uvicorn app.server:api --reload     # open http://127.0.0.1:8000  (report/copilot need the API key)
```

## Evaluate
```bash
python -m eval.test_guardrails      # deterministic guardrail eval — free, no API key
python -m eval.run_eval             # RAGAS harness -> eval/report.md (needs the API key)
python -m eval.eval_sarcasm         # regex vs LLM buy-intent on a labeled sarcasm set (needs the key)
```
The harness runs 18 eval questions through the graph and scores them with **RAGAS** on two axes —
**answer quality** (faithfulness, answer-relevancy) and **retrieval quality** (context-precision,
context-recall) — using **Claude as the judge LLM** and the same local MiniLM embeddings the
retriever uses, so one API key runs the whole project. The two retrieval metrics are graded against
an authored ground-truth `reference` per question (grounded in the synthetic corpus); recall is the
one that catches retrieval quietly dropping evidence an answer needs. It also reports a free,
non-LLM **lexical retrieval recall** (is an expected term present in any retrieved context). One
question is deliberately unanswerable ("What is the product's shipping policy?") to verify the model
refuses instead of hallucinating.
### Results

**Guardrail eval: PASS** — no matched-control or already-seeded creator is ever recommended,
under any product filter (deterministic, free, runs in CI-time).

| Metric (18 questions) | Score |
|--------|-------|
| **Answer** — Faithfulness (RAGAS) | 0.85 |
| **Answer** — Answer relevancy (RAGAS) | 0.72 |
| **Retrieval** — Context precision (RAGAS) | 0.48 |
| **Retrieval** — Context recall (RAGAS) | 0.39 |
| Lexical retrieval recall (free, non-LLM) | 0.94 |

Retrieval scores are **after** the MMR fix (failure case 6); before it they were 0.41 / 0.22.
Full per-question breakdown in [`eval/report.md`](eval/report.md).

### Failure cases the eval caught (and the fixes)

1. **Correct answers judged as hallucinations.** Every "which creators…" question scored
   *faithfulness 0* despite correct answers. Root cause: creator handles lived only in document
   *metadata*, so the judge never saw the evidence behind the attribution — and the answer model
   itself couldn't name creators until the handle was injected into the prompt. Fix: make
   documents **self-contained** (handle embedded in the text at ingest), so retrieval, the
   answer prompt, and the eval judge all see identical evidence. Faithfulness 0.70 → 0.83.
2. **A third of judge calls silently failing.** Claude 5 models reject the deprecated
   `temperature` param, which ragas sets on its judge internally — poisoning scores with NaNs.
   Fix: judge pinned to `claude-sonnet-4-5` (the answer model stays on `claude-sonnet-5`).
3. **Intermittent crash on thinking blocks.** The answer node assumed `content[0]` is text, but
   Claude 5 models may emit a thinking block first. Fix: extract all text blocks by type.
4. **Groundedness probe behaves as designed.** The unanswerable question ("shipping policy")
   scores faithfulness 1.0 with relevancy 0: the model **refuses** instead of inventing an
   answer. The low relevancy is the expected signature of a correct refusal.
5. **The same eval-blindness bug, in a new disguise (v2).** When v2 added joined "quant facts"
   (tier / GMV / seeded flags) to the answer prompt, faithfulness collapsed to 0.63 — the
   judge wasn't shown the fact lines, so correct answers citing them looked hallucinated.
   Same root cause as #1: **the eval must see exactly what the model sees.** One-line fix,
   faithfulness back to 0.82. Eval harnesses rot silently when the pipeline evolves — this is
   why the eval reruns on every corpus change.
6. **Redundant retrieval was silently capping recall — and the metric I added caught what the
   cheap check missed.** Adding **context-recall** ("did retrieval fetch *everything* the answer
   needs?") exposed a failure the lexical hit-rate (0.94) rated as healthy. Pure cosine top-8 was
   returning **near-duplicate neighbors**: *"which categories do creators fall into?"* surfaced
   only beauty + lifestyle (missing hair care and fitness entirely); *"dry/damaged hair?"* returned
   eight copies of the same comment. I had earlier written this off as a *corpus* artifact — the
   reference-free precision metric looked bad and I blamed near-duplicate synthetic text.
   Context-recall proved it was the **retriever**. Fix: **MMR (maximal-marginal-relevance)** —
   over-fetch 40 candidates, then greedily select 8 that are relevant *and* mutually dissimilar
   (`app/graph.py`). Recall **0.22 → 0.39 (+75%)**, precision **0.41 → 0.48**, answer quality
   unchanged. The residual gap is an honest k-vs-coverage limit: a few references enumerate 5–7
   exact phrases that can't all fit in 8 contexts — next lever is raising `k` or tuning λ. Lesson:
   a lexical "is a relevant doc present?" check and an LLM "is the retrieved set *complete*?" check
   are different questions, and only the second one found this bug.
7. **The buy-intent filter can't read sarcasm — and I measured exactly how badly.** The retrieval
   buy-intent signal is a cheap regex (`app/intent.py`); it matches keywords ("add to cart", "how
   much", "buy") literally, so a sarcastic comment like *"oh sure, let me add to cart another $40
   brush I don't need"* is counted as genuine purchase intent. A labeled sarcasm set
   (`eval/sarcasm_set.jsonl`, 24 comments) put a number on it: the regex flags **5 of 10 sarcastic
   comments** as buy-intent (accuracy 79%). Fix: an LLM classifier (`app/intent_llm.py`, Claude Haiku,
   batched, graceful no-key fallback) that reads tone — **0/10 false positives, 92% accuracy, 100%
   sarcasm detection** (`eval/eval_sarcasm.py`, live at `/classify` and in the Copilot tab). Honest
   scope: buy-intent density is a *soft* ranking signal — the engine's causal labels come from real
   GMV/orders, which sarcasm can't fake — so this hardens a secondary input rather than the money math.
   Lesson: keyword sentiment fails silently on irony; the only way to know how much is to label a set
   and measure it.

## Architecture
```
CSVs --ingest--> Chroma  ──►  LangGraph: retrieve ─(buy-intent filter)─► answer(Claude, cited)
                                                        │
                                          RAGAS eval ◄──┘
FastAPI:
  RAG + eval    /ask  /classify  /health
  decisions     /decisions  /allocate  /spark  /post_funnel  /heterogeneity  /recommend
  economics     /economics  /holdout  /drift  /recommender  /scorecard
  voice-of-cust /voc  /voc_actions  /theme_lift  /intent  /corpus_stats
  lookup+copilot /creator  /brief  /explain  /query
  reporting     /report  /report.pdf  /ops_brief  /samples_in_flight
                                                            •  Docker (+ headless Chromium) -> cloud

outcomes.csv  --> economics (ROI/LTV/sensitivity) + holdout (natural experiment + power) + drift (PSI)
campaigns/videos --> decision queue (verdicts) + allocator + spark timing
comments.csv  --> RAG corpus + voice-of-customer (competitor board, theme->conversion, buy-intent)
```

> **The report is the money step for a demo.** `/report.pdf` prints the entire desk as a portable
> weekly artifact; the framework is documented in [`docs/REPORT-FRAMEWORK.md`](docs/REPORT-FRAMEWORK.md)
> so it ports to any repo.

## Deploy (Docker → Render)
```bash
docker build -t creator-insight .
docker run -p 8000:8000 -e ANTHROPIC_API_KEY=$env:ANTHROPIC_API_KEY creator-insight
```
The image bakes the synthetic data + Chroma index at build time (and installs a headless **Chromium**
so `/report.pdf` renders server-side), so the container is fully self-contained; only the API key is
injected at runtime. `render.yaml` lets Render build the Dockerfile straight from GitHub — set
`ANTHROPIC_API_KEY` as a secret env var and check `/health` returns `{"ok": true}`. *(Render tip: space
out pushes — two commits seconds apart can leave it building the first and skipping the second.)*

## Tradeoffs
- **Chroma + local MiniLM embeddings** — free, offline-friendly, and zero embedding-API cost;
  one API key (Claude, generation + eval judging) runs the whole project. The tradeoff is
  weaker embeddings than hosted models — acceptable at 3.2k documents.
- **Grounded-only prompting** — the model may only answer from retrieved, numbered context and
  must cite `[i]`; it's told to refuse rather than invent. Costs some fluency, buys trust.
- **Index baked at Docker build time** — simplest possible deploy for a demo corpus; a real
  system would ingest incrementally against a hosted vector DB.
- **Regex buy-intent filter** — a cheap, auditable retrieval filter tied to a revenue signal;
  an ML classifier would generalize better but is overkill here.

## Notes
- `ANTHROPIC_API_KEY` is read from the environment (or a local `.env`); it is never committed
  or baked into the image.
- Re-running `app.ingest` rebuilds the index idempotently.
